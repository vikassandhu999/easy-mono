# Requested check-ins

When following up with a client, a coach needs to see which individual check-ins still need an answer, so they can adjust a deadline or retire an obsolete request. The schedule describes future generation; response history starts after submission. Neither lists every outstanding request. Workbench surfaces only the latest missed check-in per client.

Enter from client check-in schedules into Requested check-ins. Use a separate client-scoped list instead of expanding each schedule into another independently paginated list. Default to Outstanding, with All, Missed, Completed and Dismissed choices, server search by form name and newest-first cursor pages. Each row leads with the form name, then status, due date and priority. Completed requests link to the existing response reader. Keep scheduling and response history one link away.

Manage an outstanding request in a short dialog: due date and priority, one Save action, and a quiet Dismiss action with its own named confirmation. Dismissed requests can be reopened deliberately. These actions affect one request and preserve the recurring schedule. Never offer marking unanswered work completed. Status preconditions protect concurrent client submissions; completed requests remain read-only in this view. On any uncertain or stale write, retain the draft but require Refresh requests before attempting another change. Refresh closes the dialog only after the current list loads successfully. Preserve filters and focus the result notice. Warn before abandoning dirty or pending edits.

Use a scoped API read with summary rows, server counts/search/status and cursor pagination. Keep the existing assignment write contract. A due-date/priority update sends only changed fields and the observed status; same-field edits have no revision protection in the existing API. Do not derive completion, overdue status, counts or selection from downloaded rows.

Verify at 375px and 1280px: entry and returns, three pages and remote search, retained page/read failures, empty filters, long names, edit/cancel/dirty navigation, dismissal/reopening, real client submission and response reading, stale and lost-write recovery, preserved schedule, delayed logout and clean caches. Backend tests cover exact projection, status groups, tenant/trainer/client isolation, cursor stability and invalid input.
