# Workout concept

Status: in design, 9 October 2026. Replaces the training part of `.scratch/core-domains/` (plans, plan revisions, schedule entries) when accepted.

The attachment and exercise-gallery design is accepted in [ADR 0003](../../docs/adr/0003-shared-attachments-and-feature-media.md). The [schema review draft](models.ex) records that design; backend implementation is pending.

Prescription-specific side tracking is accepted in [ADR 0004](../../docs/adr/0004-workout-exercise-side-mode.md). It replaces the exercise-wide `unilateral` rule below.

Ordered metric entries with separate labels, and the deferral of grades, are accepted in [ADR 0005](../../docs/adr/0005-exercise-metric-labels.md).

Free-text equipment descriptions and muscle-name arrays are accepted in [ADR 0006](../../docs/adr/0006-exercise-equipment-and-muscles.md).

Exercise archiving preserves existing uses under [ADR 0007](../../docs/adr/0007-exercise-archiving.md).

Exact, range, maximum, and client-chosen numeric targets are defined in [ADR 0008](../../docs/adr/0008-numeric-target-validation.md).

## Decisions

| # | Decision |
|---|---|
| W1 | A Workout is an instruction for one training occasion. It belongs to one owner (W10). |
| W2 | Workout type says **what** is done: `prescribed` (exercise groups, W4), `video` (one uploaded video or external link through Attachment, W53), or `open` (no content; the leader decides on the spot). **When, where and with whom** belong to the schedule row (W16). A live virtual class or an in-person session is an `open` or `prescribed` workout on a schedule row with a time, a place or link, and a coach. (Replaces `follow_along`, 9 Oct 2026.) |
| W3 | What is performed is described by facets (W22). Only `kind` has behaviour; every other facet is for search, filters and reports. (Replaces the single category tag, 9 Oct 2026.) |
| W4 | A prescribed workout has exercise groups. A group has an optional name, a round count, and one or more ordered exercises (W52). "How many times" lives only in `rounds`. One exercise with 3 rounds is a straight set; two exercises in one group is a superset. |
| W5 | A workout exercise has targets the same for all rounds, or one target for each round. W51 requires exactly one entry for same_for_all or exactly the group round count for per_round, regardless of side mode. |
| W6 | Schedule: workout + client, one `date` or a `day_of_week` between `from_date` and `until_date`, optional `time`. An appointment is not a separate concept: a schedule row with a time is enough. |
| W7 | WorkoutLog: what the client did. `workout_history_id` null = free workout. Sets record `round` and values. |
| W8 | Prescription history must rebuild what was prescribed on any client date, including dates without a WorkoutLog. Preserve the schedule that applied and the workout content version it used. Past prescribed versions remain available; future-only versions can change without retaining unused drafts. Each log points to the exact version it used. This supersedes the rule that history is created only when logging starts (nutrition discussion, 9 Oct 2026). Same-day boundaries and the version storage/write mechanism remain open. |
| W9 | Copy on assign, never linked. This is the cornerstone: a library or program workout is copied to the owner that receives it, and the copy has no link back. |
| W10 | One `workouts` table with three owners: library (`client_id` and `program_id` null), program (`program_id`), client (`client_id`). Never both. A workout has no time in it, so one shape serves all owners. |
| W11 | Two schedule tables, one time system each. `schedules` (client) uses dates; `program_schedules` uses week numbers. Same shape: one occasion, or a weekday rule between two bounds. Assign translates week `w` to `start + 7 × (w − 1)` days. |
| W12 | Metrics are decided in W24–W29 and the "Metric catalogue" section. |
| W13 | An occurrence is one expected workout on one date: `(schedule_id, date)`. It is calculated from schedule rows, never stored. A log claims it with `schedule_id` + `scheduled_date` (both null for a free workout). The log date can differ from the scheduled date. Done = a log exists for the pair. |
| W14 | A schedule row never changes its facts. Fact dates: every date before today, and today only if a log claims today's occurrence; future dates are never facts. Change or delete = set `until_date` to the last fact date (and, for a change, start a new row after it); a row with no fact dates is deleted. A same-day replace is therefore a clean delete. There is no separate archive: an ended row is the archive. (Rule refined 9 Oct 2026.) |
| W15 | A change to one occurrence: `ScheduleSkip { schedule_id, date }`. Skip = one skip row; a skipped occurrence is not expected and does not count as missed. Move = a skip plus a new one-off schedule row. |
| W16 | A schedule row carries the occasion: optional `time`, `place` or `meeting_url` (at most one), and `coach_id` (the coach who leads). Example: a prescribed leg workout on "Tue 18:00, Gold's Gym, with Sam". |
| W17 | Anyone who takes part can record a log: the client, or a coach with access to the client. The log stores `recorded_by` (client or coach). The app offers recording to the leader: an occurrence with a `coach_id` shows "Start session" in that coach's app, other occurrences show "Start workout" to the client. One log per occurrence at a time; the other person sees "<name> is recording this session". Replaces M17. |
| W18 | Log states: `active` → `completed` or `discarded`. One active log per client. Workout feedback is on the log; W72–W73 define optional session effort, pain/discomfort, and one shared note. |
| W19 | Every log can have sets, whatever the workout type; for `video` and `open` they are optional. A set stores `workout_exercise_id`: the id of the prescribed exercise inside the log's WorkoutHistory copy (not a foreign key to the live workout, so later edits never break it), so only sets of a `prescribed` workout can link. Calculated, not stored: planned set (link, same exercise), swap (link, other exercise), extra set (no link). `is_quick_add` is removed. |
| W20 | `Program { id, business_id, name, description, weeks }`. Assign: the coach picks a client and a start date; each program workout is copied to the client with new ids; each program schedule row becomes a client schedule row that points to the copy. The client's existing schedule is not touched; two workouts on one day are allowed. |
| W21 | Week 1 is the calendar week (Monday to Sunday) that contains the start date. Occurrences before the start date are not created, so the first week can be short. The coach can start on any day. |
| W22 | Exercise taxonomy is locked: the facets in "Exercise taxonomy" below. Exactly one `kind`; goals and places are optional selections (W46). W43 defines equipment as optional free text and muscles as free-text names. `kind` gives the default metrics when a coach creates an exercise. |
| W23 | If a change alters the movement, it is a separate exercise (freestyle and breaststroke; back squat and front squat). |
| W24 | Metrics come only from our catalogue. W42 extends custom labels to each selected metric separately; labels never change the metric key, units, or calculations. A new kind of value is added to the catalogue once, for everybody. No coach-made metrics. |
| W25 | One target shape for every numeric metric: `exact` (value), `range` (min, max), `max` (as much as possible), or empty (the client chooses and records). "For time" = distance exact, duration empty. "Weight for RPE 8" = weight empty, effort exact 8. A target exists only on the exercise's metrics. |
| W26 | Weight has a fourth target mode: `percent` of the client's 1RM for that exercise. The 1RM is the newest of: an entered max (`ExerciseMax`, coach or client) or a logged completed single (1 rep). No estimates from formulas. The logger shows "75% · 105 kg (of 140 kg, 3 Oct)", or "no max yet: choose your weight". The logged value is always real kg. |
| W27 | Superseded by W41 on 16 Oct 2026. Side tracking is chosen per workout exercise; it is no longer controlled by an Exercise-level `unilateral` field. |
| W28 | Logged metric values are typed columns on `exercise_sets`, one per catalogue metric (`reps int`, `weight_kg numeric`, `duration_s int`, `distance_m numeric`, …), nullable. Base units plus the unit the person typed (M14). A new metric is one migration. Targets are JSON inside the workout (and its WorkoutHistory copy), checked by the app on save. |
| W29 | The metric catalogue is locked (section "Metric catalogue"). A missing value later is added to the catalogue once, by a dated decision. |
| W30 | Rest has one field with one meaning: `rest` on the workout exercise = the rest after doing this exercise, after both sides for per_side (W48). The rest after the last exercise of a group is the rest between rounds. W47 distinguishes client-chosen rest, explicit no rest, exact duration, and a range; W5 applies the same targets to all rounds or supplies them per round. Not logged; the client's rest timer uses it. Real rest, if ever needed, is calculated from set times. |
| W31 | Everything on an exercise is editable (metric list, `kind`, name). An exercise describes how to show and log it from now on; it never changes data that already exists. Removed metrics stay in old logs and reports. WorkoutHistory copies keep old names. Replaces M13. Side tracking moved to WorkoutExercise under W41. |
| W32 | Deleting a workout: apply W14 to its schedule rows first. If any row remains, the workout is archived (`archived_at`); otherwise it is deleted. Done work never needs the original: logs point to WorkoutHistory copies, so `WorkoutHistory.workout_id` is a plain id, not a foreign key. Library and program workouts have no schedule facts, so they are deleted. One sentence for W14 and W32: keep every date that is a fact; remove everything else; a row or a workout with no facts is deleted. |
| W33 | Progression across weeks needs no new concept: a program schedules a separate workout per week where targets change ("Lower A (week 1)" on a `week` row, "Lower A (week 2)" on the next). The builder offers "Duplicate for next week". Replaces the "Not now" for progression (M8). |
| W34 | *Withdrawn 13 Oct 2026 (user decision).* Logs use only their own tables (`workout_logs`, `exercise_sets`). No shared record spine, no `Easy.RecordJournal`, no `record_changes`, no `last_change_seq`. |
| W35 | Every table carries `business_id` (tenant). A library workout is `business_id` set, `client_id` and `program_id` null. Built-in exercises keep `business_id` null. |
| W36 | Workout schedule rows use `weekdays_mask` (Mon=1 … Sun=64), the same convention as nutrition (N8) and trackers (R6). One row can cover several weekdays. Replaces the single `day_of_week` in W6 and W11. (10 Oct 2026.) |
| W37 | (12 Oct 2026) History storage for W8, the same rule as nutrition N36: a workout that applied on a past date never changes. An edit before that is made in place. An edit after it copies the workout with its groups, exercises and targets; each schedule row that uses it ends on its last fact date and a new row starts on the copy (W14); the old workout is archived (W32). No version tables. WorkoutHistory copies for logs (W7, W19) stay as decided and are built with logging. |
| W38 | (13 Oct 2026) No WorkoutHistory. Under W37 a workout that applied never changes, so a WorkoutLog points to `workout_id` and an ExerciseSet to `workout_exercise_id` directly (both foreign keys). Replaces the WorkoutHistory copy in W7, W8, W19 and W32: "planned set / swap / extra set" stay calculated as in W19. |
| W39 | (13 Oct 2026) Same-day edits follow W14 for workouts and nutrition: today is a fact once a log claims today's occurrence. A coach's edit after that copies the workout or preset (W37, N36), so the client's record keeps what it followed; before any log, the edit applies to today in place. Closes nutrition open question 4. |
| W40 | (15 Oct 2026) An exercise has an ordered gallery of image/video demonstrations and external links, with an optional caption per item. `ExerciseMedia` connects the exercise to the common `Attachment` model. Separate feature relationship tables retain parent foreign keys; there is no generic `thing_type`/`thing_id` table or table with multiple nullable parent IDs. This replaces scalar `Exercise.media`; ownership columns, access, and tenant enforcement are deferred for the new schemas. See [ADR 0003](../../docs/adr/0003-shared-attachments-and-feature-media.md). |
| W41 | (16 Oct 2026) The coach selects `WorkoutExercise.side_mode`: `combined` (default) or `per_side`. Combined repetitions and duration cover the whole round, with one result using `side = null`. Per-side targets apply to left and right separately, with results using the same round number and `side = left/right`. The number of rounds does not change. This replaces Exercise.unilateral and the proposed reps_scope; see [ADR 0004](../../docs/adr/0004-workout-exercise-side-mode.md). |
| W42 | (16 Oct 2026) Exercise.metrics is an ordered collection of typed embedded `ExerciseMetric { key, label? }` values. Keys come from the fixed catalogue and are unique within an exercise; null labels use the standard catalogue label. This replaces the key-only list and shared count_label. Grade, grade_scale, and new generic choice metrics are deferred for the current personal physical-activity scope. Existing historical grade data is retained. See [ADR 0005](../../docs/adr/0005-exercise-metric-labels.md). |
| W43 | (16 Oct 2026) `Exercise.equipment` is optional free text describing equipment, alternatives, and optional items. `Exercise.muscles` remains an array of free-text names, one name per entry, without implied primary/secondary roles. No catalogues, equipment setups, or relationship tables are introduced. Blank equipment text becomes null; muscle names are trimmed and must be nonblank and unique after trimming. See [ADR 0006](../../docs/adr/0006-exercise-equipment-and-muscles.md). |
| W44 | (16 Oct 2026) Exercise has optional plain-text `instructions` explaining how to perform the activity. Trim surrounding whitespace, store blank text as null, and preserve internal text and line breaks. Instructions apply to the whole exercise; media captions describe individual gallery items. |
| W45 | (16 Oct 2026) Exercise has nullable `archived_at`, set by Archive and cleared by Restore. Archived exercises are hidden from new selection, but existing workouts can still display and log them. Archive preserves references, instructions, media, and recorded activity. Ordinary exercise edits cannot set archive state; permanent deletion remains blocked while the exercise is referenced. See [ADR 0007](../../docs/adr/0007-exercise-archiving.md). |
| W46 | (16 Oct 2026) Only name and kind are required Exercise inputs. Goals, places, and metrics can be omitted or empty. Goals/places default to []; omitted metrics on creation still use kind defaults, while explicit [] stays empty. On update, omitted selections are preserved and [] clears them. Supplied entries must remain valid and unique. This relaxes the earlier minimum-selection requirements in W22 and ADR 0005. |
| W47 | (16 Oct 2026) RestTarget defaults to `client_chooses`: leaving rest blank means no prescribed duration, not an instruction to continue immediately. `none` explicitly means no rest. `exact` and `range` retain their duration fields in seconds. This changes the review draft's earlier default of `none`; runtime behavior and stored data are unchanged. |
| W48 | (16 Oct 2026) For `side_mode = per_side`, prescribed rest occurs once after completing both sides of the exercise in that round, not after each side. The same rule applies to repetitions and duration. `RoundTargets.rest` holds the instruction; no extra side-rest field is needed. See [ADR 0004](../../docs/adr/0004-workout-exercise-side-mode.md). |
| W49 | (16 Oct 2026) CountTarget and NumericTarget validate mode-specific shapes: exact requires only value; range requires only min/max with min <= max; max and client_chooses carry no numbers. Counts are whole numbers; numeric targets use decimals and metric-specific limits. Partial updates validate the complete resulting target. Equal range bounds remain valid. See [ADR 0008](../../docs/adr/0008-numeric-target-validation.md). |
| W50 | (17 Oct 2026) RoundTargets validates each nested target through its typed changeset and accepts metric targets only for the Exercise's selected keys. Missing metrics need no prescription; rest is independent. Omitted entries are retained and revalidated on update; null clears a metric target and resets rest to client_chooses. Unknown keys and non-object/non-null targets are rejected. See [ADR 0008](../../docs/adr/0008-numeric-target-validation.md). |
| W51 | (17 Oct 2026) WorkoutExercise validates its reference against the resolved Exercise, requires valid side/target modes, and validates each nested round target. The target list contains exactly one entry for same_for_all or exactly the positive group round count for per_round; per_side does not double it. Supplied arrays replace the ordered list, omitted arrays retain and revalidate it, and no targets are silently added or removed. Empty round objects are allowed, but empty target lists are not. See [ADR 0008](../../docs/adr/0008-numeric-target-validation.md). |
| W52 | (17 Oct 2026) ExerciseGroup has an optional trimmed name, 1–100 rounds (default 3), and a nonempty ordered array of workout exercises. It resolves each child through the caller's authorized Exercise lookup and passes the group's round count into child validation. Existing occurrence IDs survive reordering; supplied IDs must be valid and unique within the group. Repeated library exercise IDs are allowed as separate occurrences. Omitted arrays retain and revalidate children. See [ADR 0008](../../docs/adr/0008-numeric-target-validation.md). |
| W53 | (17 Oct 2026) Workout.video is an association to the common Attachment model, stored as video_id. It is required for video workouts and null for prescribed/open workouts. One video slot needs no relationship table. The future writer must validate the attachment's suitability and authorization; the FK must restrict asset deletion while referenced. This replaces the scalar video URL; see [ADR 0003](../../docs/adr/0003-shared-attachments-and-feature-media.md). |
| W54 | (17 Oct 2026) Prescribed workouts can be saved with groups = [] while the coach builds them, but require at least one valid exercise group before scheduling. A group itself cannot be empty. Video workouts require their video attachment and no groups; open workouts have neither. Edits that leave a workout scheduled must also pass scheduling-level content checks. No extra draft/published status is introduced; see [ADR 0009](../../docs/adr/0009-workout-content-readiness.md). |
| W55 | (18 Oct 2026) Workout insert/update changesets validate metadata and the complete embedded group tree, using built-in or same-business Exercise definitions. Ownership and archive state are not ordinary edit inputs. Group and occurrence IDs are unique across the workout; moving an occurrence between groups preserves its ID and revalidates its targets. Creating a separate workout generates fresh embedded IDs. Save-content checks run in the changeset; the context must also apply schedule-content checks where required. Persistence, authorization, history handling, and reference synchronization remain separate. See [ADR 0009](../../docs/adr/0009-workout-content-readiness.md). |
| W56 | (18 Oct 2026) A new WorkoutSchedule defaults an omitted from_date to the client's current local date. The coach can choose a future start date; the writer must preserve that choice. The stored start date is required. On update, an omitted start retains the existing date, and W14 still protects schedule facts. This is a context-level creation default, not a static schema default. The review draft records this rule; the runtime writer still forces today and must change during implementation. |
| W57 | (18 Oct 2026) WorkoutSchedule.until_date is optional and inclusive, using the client's local calendar. Null repeats the selected weekdays until the schedule is stopped. A supplied end must be on or after from_date; equal bounds are allowed. For one week only, the coach can select that week's Sunday as the end. Only weekdays selected by weekdays_mask occur within the date window. Draft validation is implemented under W63; runtime integration remains pending. |
| W58 | (18 Oct 2026) A WorkoutSchedule date window must contain at least one weekday selected by weekdays_mask. Reject a bounded window with no matching day, for example Monday selected within a Tuesday–Thursday window, with "Select a weekday within the date range." Equal start/end dates are valid only if that date's weekday is selected. An open-ended window with a valid nonempty weekday selection always contains a match. Draft validation is implemented under W63; runtime integration remains pending. |
| W59 | (18 Oct 2026) WorkoutSchedule.time is optional and uses the client's timezone. Null means the workout can be completed anytime on its scheduled date; 00:00 explicitly means midnight. The same time applies to every weekday selected by the row. Different times require separate schedule rows. This records the approved rule in the review draft; runtime enforcement and timezone handling remain implementation work. |
| W60 | (18 Oct 2026) WorkoutSchedule.place is optional free text. WorkoutSchedule.meeting_url is an optional full HTTP or HTTPS URL with a host. Trim surrounding whitespace for both fields and store blank values as null. W16 still permits at most one of place and meeting_url to be set; both may be null. Draft validation is implemented under W63; runtime integration remains pending. |
| W61 | (18 Oct 2026) WorkoutSchedule.coach_id is the optional coach who leads the session (W16); null means no assigned leader. A newly selected coach must be active and belong to the schedule's business. Removing a coach later must preserve references on past sessions. This records the approved rules in the review draft; selection validation and reference protection remain implementation work. |
| W62 | (18 Oct 2026) WorkoutSchedule requires business_id, client_id, and workout_id. The business comes from the authorized context; the client belongs to that business, and the workout belongs to that same client and business. A library workout is copied to the client before scheduling (W9). The schedule retains client_id for direct client filtering and ownership constraints; composite foreign keys must enforce matching ownership. Business and client stay fixed after creation; assigning to another client creates a separate schedule. This records the approved rules in the review draft; writer enforcement and database integration remain implementation work. |
| W63 | (18 Oct 2026) WorkoutSchedule has structural insert/update changesets in the review draft. Insert takes trusted ownership/reference IDs and the client's local today; supplied dates override the creation default. Ordinary input cannot change identity, ownership, or workout reference. Changesets validate required UUIDs, weekday masks, inclusive date bounds, matching weekdays, optional time, and normalized location fields, including the complete resulting state on partial updates. Database constraint registrations do not create or execute constraints during draft checks. Authorization, reference resolution, active-coach selection, workout readiness, timezone handling, and history-preserving persistence remain context work. See [ADR 0010](../../docs/adr/0010-workout-schedule-validation.md). |
| W64 | (18 Oct 2026) WorkoutLog requires business and client ownership and retains three reference cases: a scheduled session has workout_id, schedule_id, and scheduled_date; a saved workout performed outside its schedule has only workout_id; training without a saved workout has all three null. schedule_id and scheduled_date must be set together or both null. A scheduled log's workout must match the schedule, and all linked records must belong to the same client and business. scheduled_date identifies the planned occurrence; date records when the client actually trained and may differ (W13). This records the approved rules in the review draft; draft log validation remains pending. |
| W65 | (18 Oct 2026) Discarding a WorkoutLog retains the log and its sets but excludes that attempt from completed-workout totals. A discarded attempt does not claim its scheduled occurrence, so the client can start a new attempt for the same occurrence. The original attempt retains its schedule references for history. This refines the state behavior in W18 and occurrence claims in W13; draft lifecycle validation and runtime integration remain pending. |
| W66 | (18 Oct 2026) A completed WorkoutLog can be explicitly reopened for corrections: completed -> active -> completed. Reopening retains the same log and its sets. It is allowed only when the client has no other active log, preserving W18's one-active-log rule. This records the approved behavior in the review draft; draft lifecycle validation and runtime integration remain pending. |
| W67 | (18 Oct 2026) WorkoutLog.date is the required actual training date in the client's local calendar. On creation, an omitted date defaults to the client's local today. Past dates are allowed; future dates are rejected. The date can be corrected while the log is active, including after reopening, without changing scheduled_date. For Monday's planned workout performed Tuesday and entered Wednesday, scheduled_date remains Monday and date is Tuesday. This records the approved rules in the review draft; draft validation and runtime integration remain pending. |
| W68 | (18 Oct 2026) WorkoutLog.time is the optional actual start time in the client's timezone. Null means the time was not recorded; 00:00 means midnight. There is no automatic default or copy from the scheduled time. The time can be corrected while the log is active, including after reopening. A log can be completed without a start time, so recording a past workout does not require inventing one. This records the approved rules in the review draft; draft validation and runtime integration remain pending. |
| W69 | (18 Oct 2026) Remove WorkoutLog.at_utc from the review draft. The current backend assigns it the server time when creating the log, which duplicates inserted_at's business purpose. Use inserted_at for log creation time and date plus optional time for actual training. The runtime field, stored data, API, and consumers remain unchanged until implementation. |
| W70 | (18 Oct 2026) WorkoutLog.recorded_by is a required client/coach enum, replacing the user UUID in the review draft. For client recording, the existing client_id identifies the recorder and coach_id must be null. For coach recording, coach_id is required and identifies the original recording coach in the same business, who may differ from the schedule's session leader. The server sets the recorder from the authorized coaching context; later edits and reopening preserve it. No user reference is stored on the proposed log. Draft changesets, database migration, runtime writers, and API changes remain pending. See [ADR 0011](../../docs/adr/0011-workout-log-recorder.md). |
| W71 | (18 Oct 2026) WorkoutLog.text is an optional plain-text note about the whole session. Trim surrounding whitespace, store blank text as null, and preserve internal text and line breaks. Keep the existing maximum of 10,000 characters and apply it on both creation and edits. The note is editable while the log is active, including after reopening. It stays attached to the log; sending a message to the coach is a separate action. This records the approved rules in the review draft; draft validation and runtime integration remain pending. |
| W72 | (18 Oct 2026) Workout feedback helps the coach adjust the next workout and describes the client's experience, including when a coach enters the answers. The selected direction is optional session effort, a separate optional pain/discomfort answer, and one shared note. All feedback can be omitted when completing a log; missing answers remain unknown. Session effort uses whole numbers 1–5: 1 Very easy, 2 Easy, 3 Moderate, 4 Hard, 5 Very hard, with no default. It rates the whole session and is not calculated from set effort; an easy rating does not imply an unsuccessful workout. W73 applies the selected fields to the review draft. |
| W73 | (18 Oct 2026) Apply the approved feedback block to the review draft: effort is a nullable integer from 1 to 5, pain is a nullable boolean, and text is the shared optional note under W71. | W74 | (18 Oct 2026) A swap selects a replacement for the remaining unrecorded sets of one prescribed workout entry in this log. ## Exercise taxonomy (locked)

Each facet answers one question. Its values do not overlap.

| Facet | Question | Values | Per exercise |
|---|---|---|---|
| **Kind** | What shape does the effort have? | **movement**: repeated in sets (squat, push-up, plank) · **activity**: continuous, covers time or distance (run, swim, cycle, hike, row) · **sport**: play with rules and a result (football, tennis, basketball) · **practice**: a guided form (yoga, Pilates, meditation, breathwork, martial-arts forms, drills) | exactly 1 |
| **Goal** | What does it train? | strength, endurance, power, mobility, balance, skill, recovery | 0 or more |
| **Place** | Where is it done? | gym, home, outdoor, pool, court/field, studio | 0 or more |
| Equipment | What is needed? | free-text description, including alternatives and optional items | optional |
| Muscles | What does it load? | free-text muscle names, one per entry | 0 or more |

## Metric catalogue (locked)

W82 defines the recording scopes and explicit average fields in the review draft. The Report column below lists candidate statistics, not unconditional sums or averages across parent and child results. Calculations must identify their coverage; reserve remains set-only, tempo remains target-only, and duration results retain fractional seconds.

Rules:
- We define the catalogue, so reports work for every exercise.
- An exercise can choose an ordered list of typed metric entries, or leave it empty. Each entry has a catalogue key and an optional label. The coach builder, the client logger and the reports use those keys and their display order.
- Store what the person entered. Calculate the rest (pace, volume, accuracy). No formula estimates (W26).

| Group | Metric | Stored as | Shown as | Report |
|---|---|---|---|---|
| Amount | reps | count | "reps" or the exercise's label ("laps", "waves") | sum |
| | weight | kg (negative = assistance) | kg, lb | max; volume = weight × reps |
| | duration | seconds | s, min, h:mm:ss | sum |
| | distance | metres | m, km, mi, yd | sum |
| | elevation gain | metres | m, ft | sum |
| | height | cm | cm, in | max |
| | calories | kcal | kcal | sum |
| Intensity | speed | m/s | km/h, mph, pace min/km, min/mi, min/100 m | avg, best |
| | incline | % | % | avg |
| | level | 1–N (machine setting) | "Level 8" | avg |
| | power | watts | W | avg, max |
| | cadence | per minute | rpm, spm | avg |
| | heart rate | bpm | bpm | avg, max |
| | effort | RPE 1–10 | RPE | avg |
| | reserve | RIR 0–10 | RIR | avg |
| Outcome | successes / attempts | 2 counts | "7 / 10" | accuracy % |
| | score | number | points | sum, best |
| | result | win / draw / loss | — | record (W–D–L) |
| Set facts | side | left / right (null = combined result, W41) | "L / R" | per side |
| | tempo | text (target only) | "3-1-1-0" | — |

Default metrics by kind: movement → reps, weight · activity → distance, duration · sport → duration, result, score · practice → duration.

Examples: treadmill → duration, distance, speed, incline · free throws → successes / attempts · climbing practice → reps ("Moves completed"), attempts ("Route attempts"), successes ("Routes completed") · hike → distance, duration, elevation gain, weight (pack).

Grade scales and generic coach-defined choice measurements are deferred under W42. Existing historical grade prescriptions and results must remain readable. The other existing catalogue keys, including result, are unchanged by this decision.

## Workout builder UX (decided 10 Oct 2026)

Settled with a clickable prototype: route `/prototype/workout-builder` in the coach app (`frontend/apps/coachapp/src/workout-builder-prototype/`). The prototype compared cards, a sheet and an outline; cards won. It was then reviewed with the dembrandt UX skills (hierarchy, density, accessibility, information architecture).

| # | Decision |
|---|---|
| U1 | Layout: one card per group, one chip per target (`Reps 5`, `Weight 75% 1RM`, `Rest 3:00`). Tapping a chip opens an inline target editor under the exercise; only one is open at a time. |
| U2 | The target editor shows the target types the metric allows (W25, W26) and a one-line hint of what the client will see. On a phone the types form a two-column grid. |
| U3 | "Same for all N rounds / Different per round" (W5) lives in the target editor, not on every exercise. Per-round targets show as a small round × metric table. |
| U4 | The word "group" is never shown. A card's label comes from its exercise count: `A · Straight sets`, `B · Superset`, `C · Circuit`. Other text uses the card's name, or its letter. |
| U5 | A summary line under the card name says what happens: `Rest 3:00 between rounds` or `B1 → B2, then rest 1:30–2:00`. |
| U6 | "Add exercise" at the end of the workout adds a new single-exercise card (3 rounds). "Add exercise (superset)" inside a card adds to that group. There is no "Add group" and no empty group. |
| U7 | Adding an exercise to a group moves the rest between rounds to the new last exercise and sets the rest after the previous one to none (W30). |
| U8 | Untouched targets show `Any` on chips (client chooses); the editor names it "Client chooses". No rest shows `None`. |
| U9 | Density: desktop shows one row per exercise (code, name, chips, remove); a phone stacks them. Exercise kind is not shown while building; `each side` is a tag because it changes targets. |
| U10 | Remove (card or exercise) acts at once and shows "<name> removed." with Undo for 8 seconds. No confirm dialog. |
| U11 | Reordering is a separate mode: move cards and exercises up or down with buttons, and give an exercise another letter to pair it into a superset or circuit. No drag-and-drop, no "⋯" menu. |
| U12 | The exercise picker is a centered modal (a bottom sheet on a phone) with search; each result shows kind, `Each side` and its metrics. |
| U13 | Autosave: every change saves. A sticky bar shows "Saving…" / "All changes saved", or "Not saved. Your changes stay on this device." with Retry. No Save button. |
| U14 | Names have visible labels: "Workout name", "Instructions for the client (optional)", and the card label above each card name. |

Open for the real build: video and open-session panels are placeholders; the exercise picker uses a small sample library.
