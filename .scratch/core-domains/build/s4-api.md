# Slice 4 API contract

All coach paths start `/v1/coach`; client paths start `/v1/client`.

- `GET /review-roster`: query `cursor`, `limit`, `q`, `sort` (`name`, `due`, `last_reviewed`, `assessment`, `unread_chat`, `waiting_since`), `direction` (`asc`, `desc`), `due` (`due`, `not_due`, `overdue`, `inactive`), `assessment`, `unread` boolean, `waiting` boolean, `last_reviewed` (`never`, `reviewed`). Returns `{data: ReviewRosterRow[], count, next_cursor}`. Row: `{client_id, full_name, preferred_name, focus, review_frequency_days, due, overdue_days, due_on, last_reviewed_at, assessment, unread_chat, waiting_since, current_term}`. Null last review means Never this term. Nullable assessment is the latest saved assessment across history. Cursor supports every sort.
- `GET /clients/:client_id/review-screen?from=YYYY-MM-DD&to=YYYY-MM-DD`: `{data: ReviewScreen}`. Screen: `{client: Client, snapshot_token, seen_at, reviewed_through_seq, from, to, last_review: Review|null, changes: ReviewChangeGroup[], training: TrainingOccurrences, nutrition_days: NutritionDay[], trackers: TrackerMetrics[], requests: TrackerRequest[], plans: ReviewPlanLink[]}`. Existing TrainingOccurrences, NutritionDay and TrackerMetrics carry record ids and target revisions. Plan links: `{id, name, domain: training|nutrition}`. Change groups: `{record_type: workout|meal|tracker_entry, record_id, changes: ReviewChange[]}`. Changes: `{seq, row_type, row_id, action: added|changed|removed, old_value: dictionary|null, new_value: dictionary|null, changed_at}`. Old/new dictionaries contain JSON values. All fields come from one repeatable-read snapshot.
- `POST /clients/:client_id/reviews`: `{snapshot_token, assessment, private_note?, reply?}` returns `{data: Review}` with 201. A signed token binds the screen read to the actor, business, client, timestamp and sequence. A current term is required.
- `PATCH /clients/:client_id/reviews/:id`: `{assessment?, private_note?, reply?}` returns `{data: Review}`. Omitted reply is unchanged; null or blank removes it. Reviewed facts stay fixed.
- `GET /clients/:client_id/reviews?cursor=start&limit=20`: `{data: Review[], count, next_cursor}`.
- Review: `{id, client_id, coach_id, coach_name, reviewed_at, reviewed_through_seq, seen_at, assessment, private_note, reply: ChatMessage|null}`. Assessment is `on_track|needs_attention|at_risk`.
- Existing `PATCH /clients/:id` gains `focus: string|null` (one line, max 255) and `review_frequency_days: 1|3|7|14|28`. `Client` gains both; `ClientProfile` gains `focus`.
- `GET /review-settings`: `{data: {default_review_frequency_days}}`; `PATCH /review-settings`: `{default_review_frequency_days, apply_to_existing?: boolean}`. Owner writes; all coaches read. Default 7.
- Client `GET /review-replies?cursor=start&limit=20`: existing `ChatMessageHistory` page filtered to review references. No review assessment or private note is available to clients.
- `ChatMessage` gains nullable `edited_at`; response `embed.type` gains `review`. General chat creation does not accept review references. Review reply mutations are transactional. Channel events: `message_updated` contains ChatMessage; `message_deleted` contains `{id}`. Inbox uses existing conversation update notification.

Summary ranges permit 366 inclusive days. Default begins at the last review date, otherwise the current term start, capped to 366 days. New changes are independent of the selected summary range. The full current term journal is read when this term has no review.

Implemented additions: roster rows also include `id` (same as client_id), `state`, `email`, `phone`, `coach_name`; roster supports `state` filter. Screen has `training_counts: {expected, completed, extra}` and `nutrition_summary: {days_logged, days_count, average: NutrientTotals}`. Average known_entries/total_entries count days here. Any unknown logged day keeps that nutrient average unknown. Empty meal headers do not count as logged days. Change groups have `title` plus nullable `local_date` and `tracker_id` for source links including removed entries. Client reply history accepts optional `review_id`.

Create requests use the snapshot token as a retry identity. The same token and body return the saved Review and original reply; a changed body returns conflict. Tokens expire after 24 hours and bind the current term. Review timestamps use microseconds. Rosters read tenant-visible clients, latest reviews, unread counts and open-request dates in bounded batch queries, then sort/filter/page on the server. All column sorts support cursors with an id tie-break.
