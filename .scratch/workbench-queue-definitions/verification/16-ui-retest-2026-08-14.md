## Findings

### UI-01 — Programming rows overflow and clip at 375px

- Route/state: `/clients?view=programming`, All filter, populated queue, 375×780.
- Severity/class: objective visual defect.
- Evidence: `/private/tmp/ticket16-programming-mobile-current.png`; first row measured `341px` wide with `scrollWidth=354px`, and Drew's 36px avatar began at x=4 while the bordered row began at x=17.
- Root cause: the production priority row omits the locked prototype's `items-stretch`; HeroUI's row alignment therefore centers an intrinsic-width identity child wider than the row.
- Status: fixed in `programming-view.tsx`; the accepted `items-stretch` constraint is restored. Live width probe pending because the user-owned server is stopped.

### UI-02 — Accepted queue layouts were only partially ported

- Routes/states: populated Onboarding, Programming, and Replies at mobile/desktop.
- Severity/class: locked-spec/system inconsistency.
- Evidence: exact source comparison against accepted Onboarding B, Programming A, and Replies B prototypes.
- Discrepancies:
  - Onboarding uses the generic four-column queue row at mobile instead of the accepted two-column identity + controls-below layout; it omits the reason chip and reverses Call/action order.
  - Programming places the filter inside the bordered list surface, omits the accepted section bands/descriptions and reason chips, and positions the service icon beside the name instead of the absolute coverage fact.
  - Replies desktop renders two separate inner cards with a gap instead of one split surface; its selected pane omits the accepted avatar/meta/message-preview hierarchy.
- Status: fixed in source across `onboarding-view.tsx`, `programming-view.tsx`, `replies-view.tsx`, and `workbench-screen.tsx`. Live visual confirmation pending because the user-owned server is stopped.

### UI-03 — Prototype explanation leaked into the production Replies pane

- Route/state: `/clients?view=replies`, populated selected conversation, mobile and desktop.
- Severity/class: system inconsistency / copy defect.
- Evidence: user screenshot plus live DOM probe; both contained “Waiting is separate from read state” and its implementation explanation between the message preview and actions.
- Root cause: the prototype's decision-explainer `Alert` was copied into `SelectedTaskContent` instead of remaining prototype-only.
- Status: fixed in `replies-view.tsx`. Live DOM probe changed from both strings present to both absent, while Reply and Mark handled remained; visually verified at 375×780 and 1280×800.

### UI-04 — Programming hid required facts on mobile

- Route/state: `/clients?view=programming`, populated All filter, 375×780.
- Severity/class: objective visual defect / locked-spec mismatch.
- Evidence: all three coverage facts had `scrollWidth > clientWidth` (209>119, 170>132, 211>156) and rendered with ellipses, despite the accepted mobile contract retaining the full facts.
- Root cause: an unconditional `truncate` class on the fact text while a reason chip consumed the remaining row width.
- Status: fixed in `programming-view.tsx`; all three facts now have `scrollWidth == clientWidth`, `white-space: normal`, and a two-line 28px height at 375px. Desktop retains truncation.

### UI-05 — Replies desktop double-framed the split pane

- Route/state: `/clients?view=replies`, populated selected conversation, 1280×800.
- Severity/class: system inconsistency.
- Evidence: the split grid and its `ViewShell` parent both computed a 1px border and 17px radius on the same boundary.
- Root cause: `RepliesView` created another bordered `Surface` inside the bordered surface already owned by `ViewShell`.
- Status: fixed in `replies-view.tsx`; the inner grid now computes a 0px border/radius while the `ViewShell` owner retains its 1px border and 17px radius.
