# Intake and check-ins

A client opens a request from their coach, answers it, and returns knowing the response is saved. Pending work and history are separate views of the same mobile list. The server owns membership, ordering, filtering, count, and cursor; the app follows `next_cursor` unchanged.

Use one scrollable form grouped by the coach's sections. A question-at-a-time wizard adds navigation and makes reviewing related answers harder, so reserve it for evidence of a real usability need. Keep a reachable Submit response action and show required labels before submission. Use the established shadcn Select, plain radio choices for yes/no, and appropriate mobile keyboards. Saved responses use the frozen question snapshot, with the saved time and a return link.

Entry: a pending action on Today or the Forms destination. Exit: server-confirmed response, then back to pending work. Empty pending state says there is nothing to complete; history distinguishes completed, missed, and dismissed requests. Initial/load-more errors have separate retries. A failed detail read never opens an empty editable form.

Drafts use the verified client and assignment ID, survive restarts and rejected login, and clear on explicit logout. Preserve the template identity with the draft and handle changed questions explicitly. Disable submission during uploads. Read back assignment status after a lost submission response before allowing another attempt; the existing backend locks the assignment and rejects a second submission after completion. The UI must show that saved response rather than treating it as a generic validation failure.

Backend preparation: replace the unbounded client assignment index with the repository's `CursorPage` response (`data`, filtered `count`, `next_cursor`), default limit 20, max 100, newest timestamp plus ID order. Optional `state=pending|history` and `purpose=intake|check_in` filters are applied before both paging and counting. Pending means the backend's open statuses; missed and dismissed requests cannot be submitted. The same client/tenant scope applies to page rows, counts, detail, submissions, and attachments.

Verify with real router tests for cursor continuation, tied timestamps, deleted anchors, empty data, invalid input, filtering/counts, and account/tenant isolation. Then exercise all supported answer types, save/read-back, stale-template recovery, lost-response deduplication, photo upload failure/retry, and draft restoration in mobile browser and native apps. Native photo permissions and denial recovery remain part of this workflow, not a browser-only substitute.

## Implemented slice, 2026-09-19

The mobile pending/history list, all ten question types, grouped editor, local drafts, and frozen saved-response reader are implemented. The shared list follows opaque cursors and displays the server count. A real 22-request browser scenario proves a failed second page retains the first 20 rows and retry retrieves the remainder.

Every new-app submission sends its observed template revision. The backend locks that template while validating and freezing the response, then retains the assignment lock that prevents duplicate completion. Stale revisions refresh the form; unchanged answers are restored and changed answers remain available for comparison. Changed photo questions require explicit reuse of earlier photos. `expected_revision` remains optional for compatibility with existing callers; this is not universal stale-write enforcement for older clients. Error responses continue through the repository's generic `ApiError` boundary rather than a newly introduced form-specific error schema.

The detail contract now supplies the server-resolved weight unit. Drafts retain that unit, submissions send it, and the saved question snapshot records it alongside the resulting weight entry. A later preference change cannot reinterpret an interrupted numeric answer. Older responses without recorded units say so instead of guessing from current preferences.

A lost response triggers a read-back. Only matching saved answers and units count as the same successful operation. A different response saved elsewhere preserves local work and offers comparison and explicit discard. Drafts and IndexedDB photo blobs are cleared on explicit logout; expired login retains account-isolated work.

Photos are stored locally before upload and can be retried or removed after reload. Saved-image download failures expose a retry action. The small native adapter uses Capacitor Camera 8.2.4, records picker intent, and handles Android `appRestoredResult` without automatically submitting a form. See the [official Camera API](https://capacitorjs.com/docs/apis/camera). The gallery adapter and native recovery are verified separately in [native photos](native-photos.md), including real object storage. Browser fault tests simulate the object-storage boundary; Phoenix validation, metadata, submissions, and PostgreSQL are real.

Upload tickets persist with the photo before the object upload begins. Retrying after restart reuses an unexpired ticket, and concurrent retries for the same photo share one request. Removed photos cannot be recreated by a late upload completion. A browser regression checks that a failed upload followed by reload and retry creates only one attachment ticket.
