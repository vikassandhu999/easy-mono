# Billing and client seats

When my client roster grows, I need to see available capacity and deliberately add seats, so invitations do not interrupt coaching. The business owner uses this occasionally on phone or desktop; trainers need a readable capacity view. The costly mistakes are treating pending payment as confirmed capacity, changing a subscription twice after a lost response, and cancelling without understanding when paid capacity ends.

The account menu opens Billing. Lead with used and available client seats, then subscription status, monthly cost and renewal/end date. Explain that active clients and pending invitations occupy seats. Server totals and action availability own every persisted calculation. Disabled billing and unavailable pricing are explicit states. Recent billing activity is a bounded server-selected preview, not a locally computed summary.

A pricing-card grid would force owners to compare plans the product does not have. Use one capacity summary with a progressive Add seats form: choose a quantity, review the additional monthly amount, then confirm. New subscriptions open Razorpay checkout; existing subscriptions update through the server. Payment callback is only a prompt to verify with the server, never proof of payment. Cancellation has a separate confirmation explaining free capacity and the period end. An owner can check provider status after interrupted payment. Trainers see the same capacity without payment controls.

Retain loaded data during refresh failures. Keep quantity after validation/provider failures. An uncertain write requires checking the saved provider state before another purchase; do not automatically repeat checkout. Keep payment controls pending, close hosted checkout on route/account departure, and reject late responses after session changes. A hosted-checkout loader failure can retry opening the same checkout without creating another subscription.

Verification: real local API at 375px and 1280px, isolated database/local mail and a fake provider boundary only. No real charge or subscription change. Cover free/active/past-due/cancellation/disabled states, server totals, owner/trainer access, checkout success/dismiss/load failure, refresh and uncertain writes, reload, cancellation and cross-account responses. Build, scoped Biome, repository checks and full backend precommit must pass. External integration follows the official Razorpay Standard Checkout contract: https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/.

If the first subscription-creation response loses its provider ID, the UI retains the checkout request reference and blocks a second create. Support can resolve this through `Easy.Billing.recover_checkout(ctx, request_id, subscription_id)` in an application console. Use an owner Ctx for the affected business, the request UUID shown by the application, and the subscription ID found in Razorpay using `notes.checkout_request_id`. The operation fetches the subscription and verifies its request reference, configured plan, quantity and recoverable status before linking it. A mismatch returns an error without changing capacity. An active subscription completes locally; a created or authenticated subscription returns the same checkout to resume. This is an operator recovery path, not automatic discovery of an unknown provider ID. Regression tests cover both accepted recovery and mismatched references.
