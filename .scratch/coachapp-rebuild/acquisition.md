# Coaching page and applications

When someone asks about my coaching, I need one clear page I can share, so they can understand the programs and apply without creating an account. I maintain this occasionally on a phone or laptop; the visitor usually arrives on a phone. The costly mistakes are publishing unfinished copy, losing application context when programs change, and enrolling someone twice after a lost response.

The account menu opens Coaching page. A saved page shows its status, share address, visitor preview and Edit page. An empty business gets a short explanation and Create page. The editor has three sections: introduction, programs, application. Start with headline and page address; use the business handle as the initial address. Supporting details and layout choice are optional. The published preview is the same rendering used for anonymous visitors, with preview actions clearly disabled. Save draft keeps a new page private. Publish and Publish changes are explicit actions; Take page offline has a confirmation. Unsaved changes and failed saves retain the draft.

Compared a template-first wizard with a content-first editor. Choose the editor: coaches can write what they know, leave optional content out, and preview the result without finishing artificial steps. Programs and questions use compact ordered rows with names as the hierarchy; open supporting fields only when editing them. Keyboard move controls accompany ordering. Use existing shadcn fields and selects.

The public route is independent of sign-in. Visitors choose a program or a general application, leave a name and email or phone, answer the page's questions and submit. Confirmation states what happens next and offers the business WhatsApp contact when available. No invented outcomes, proof statistics, prices or testimonials. A missing or offline page has a clear unavailable state. Failures retain visitor input; a lost submission requires idempotent recovery before a second application can be created.

Applications will have server search, status filters, totals and cursor pagination, plus a detail reader with the submitted program/questions frozen in time. Coaches can add notes, mark reviewing/lost and enroll into the existing client invitation workflow. Enrollment retains the server's seat checks and idempotency. No frontend-derived persisted counts or business selections.

Backend inspection found the existing page upsert replaces program rows on every save, and application answers currently lack frozen question labels. Resolve this before calling the public journey complete. Check concurrent edits and application submission, URL validation, permissions, old-page links, pending writes and account replacement against real routes. Current APIs allow coach page edits; preserve that permission model unless the implementation establishes a stricter server-owned rule.

Verify the authoring → preview → publish → anonymous apply → coach review → enrollment journey at 375px and 1280px, including draft/offline views, all layouts/field types, multiple pages, search, failed and lost writes, keyboard use and session isolation. Build, scoped Biome, generated API checks, repository checks and backend precommit are required. No production publication or real-user messages.

## Applications inbox design

When I receive interest in coaching, I need to find the applicant, understand their goals and decide what happens next. This is a frequent phone/desktop task. A board would make comparing stages easy but makes long applications and keyboard movement harder; choose a searchable list with a status control and a dedicated reader. Applications joins the main navigation and the coaching-page overview links to it.

Default to new applications, with explicit All, In review, Accepted and Closed filters. The server supplies search, total results, stage counts and cursors. Opening an applicant preserves list filters and position. The reader leads with name, submitted program, contact details and original question/answer rows; review status and private notes form one explicit save. Merely opening an application does not change its status. Accepted applications with a linked client show that client and keep their historical accepted status.

Enroll as client opens a short confirmation form with server-prepared name/contact defaults and the existing default-intake and seat rules. It creates the invitation through the existing backend enrollment transaction. Show a linked client after success or recovered response; never repeat an uncertain write with changed values. Revision checks protect notes/status and the first enrollment attempt. A second enrollment returns the existing client, including if the response to the first request was lost. Draft navigation, seat-limit recovery, tenant/session changes and delayed responses are part of this journey.

## Address-change recovery

A visitor may lose the submission response while the coach changes their share address. Bind the request to the published page's stable ID as well as its request UUID. Resolve the receipt through that page, and return it only for an identical request fingerprint. Creating an application still requires the URL and page identity to agree, so a reused address cannot redirect a queued submission to another business. Keep legacy requests without a page ID compatible at their original address. The browser must retain the stable ID with the pending body across reloads. Verify recovery after rename/offline and after another business claims the old address, plus rejection of mismatched page identities and changed-body replay.

Implemented and verified: public pages expose their ID; submitted requests retain it in session storage and use it to locate the original receipt. The router regression verifies rename, offline, reassigned address, changed-body conflict and refusal to create under a mismatched page identity. Legacy stored requests without an ID retain their original-address behavior; rename recovery requires the stable ID. Recovered confirmations name the original business and stay on the receipt rather than reopening a potentially reassigned address.
